# 多饮品视频流识别与业务事件系统

## 一、整体目标

摄像头持续采集视频流，系统实时识别画面中的饮品目标，并通过多帧分析、目标跟踪、饮品特征检索和手势/动作识别，最终判断设备发生了什么业务行为，例如“设备001取出可口可乐330ml”或“设备001放入某饮品”。

## 二、整体流程

摄像头视频流 → 视频流接入服务 → 实时帧流 → 目标检测 → 目标跟踪 → 饮品特征提取 → Milvus向量检索 → 多帧结果融合 → 手势/动作识别 → 业务事件生成 → RocketMQ → 业务系统。

完整链路：

Camera → Stream Ingest → Frame Stream → Detection → Tracking → Recognition → Temporal Aggregation → Gesture/Action → Business Event → RocketMQ → Business System

## 三、视频流接入

设备持续向Stream Ingest服务推送视频流。

Stream Ingest负责：

1. 接收视频流；
2. 生成streamId；
3. 为视频帧建立frameId和timestamp；
4. 将实时帧送入实时处理链路；
5. 将需要保留的原始视频或关键帧写入对象存储，用于历史回溯、问题排查和模型分析。

不要将所有视频帧的Base64长期存入Redis。Redis主要用于实时流式数据和状态管理，视频本身应该放在对象存储或专门的视频存储中。Redis Streams支持有序事件、Consumer Group、ACK、重放和Retention，可以用于实时事件流，但需要控制Stream的保留长度或时间，避免无限增长。

## 四、帧数据标识

实时帧至少需要：

deviceId：设备ID

streamId：一次视频会话ID

frameId：设备或接入服务生成的递增帧ID

timestamp：帧采集时间

frameUri/frameRef：帧在对象存储或缓存中的引用

width：图片宽度

height：图片高度

fps：视频流帧率

其中deviceId用于确定设备，streamId用于确定一次视频会话，frameId用于精确定位帧，timestamp用于时间排序和事件时间判断。

## 五、设备事件

设备开始/结束视频流时产生StreamStarted、StreamStopped事件。

StreamStarted：

eventId、eventType、deviceId、streamId、timestamp

StreamStopped：

eventId、eventType、deviceId、streamId、startTimestamp、endTimestamp

RocketMQ主要承载业务事件和生命周期事件，而不是承载每一帧图片。RocketMQ消息可以通过Topic、Tag进行分类，并使用业务唯一标识作为Keys，方便消息定位和问题排查。

## 六、目标检测

Detection Service从实时帧流获取图片，检测图片中的饮品目标。

输入：

streamId、deviceId、frameId、timestamp、frameRef

输出：

streamId、deviceId、frameId、timestamp、detections、modelVersion

每个Detection包含：

box坐标：x1、y1、x2、y2

class：beverage

score：检测置信度

boxId：当前帧中的目标ID

Detection模型只负责回答：

“这一帧中的哪里存在饮品？”

不负责判断具体是什么饮品。

## 七、目标跟踪

由于视频是连续帧，同一个饮品会在多个帧中重复出现，因此需要Tracking Service将不同帧中的同一个饮品关联起来。

例如：

Frame 100：Box A → trackId=001

Frame 101：Box B → trackId=001

Frame 102：Box C → trackId=001

虽然每一帧的Box坐标不同，但它们都属于同一个饮品目标。

因此后续识别和动作分析应该以trackId为核心，而不是简单地以frameId为核心。

## 八、饮品识别

Recognition Service根据Tracking得到的饮品目标，从原图中Crop出对应的饮品区域，然后使用Feature Extractor提取Embedding。

Crop → Feature Extractor → Embedding → Milvus → Top-K相似饮品

Recognition输出：

deviceId

streamId

frameId

timestamp

trackId

productId

Top-K候选

similarity

modelVersion

Crop区域信息

Recognition Service负责回答：

“这个track对应的饮品最可能是什么？”

## 九、多帧融合

不需要对同一个饮品的每一帧都进行完整识别。

对于同一个track，可以从多个时间点选择高质量帧进行识别，并建立时间窗口。

例如：

Frame 100 → Coke 0.81

Frame 103 → Coke 0.88

Frame 106 → Coke 0.92

Frame 109 → Coke 0.95

Frame 112 → Coke 0.94

Temporal Aggregation根据多个帧的Recognition结果进行融合，可以使用Top-K平均、加权平均、EMA、Majority Vote等方法，最终得到稳定的Product ID和Confidence。

多帧融合的目标是降低单帧由于遮挡、反光、模糊、角度变化导致的误识别。

## 十、手势/动作识别

Gesture/Action Service不应该只看单帧，而应该结合一段时间内的track变化、目标位置变化以及手部状态进行动作判断。

可以先识别基础视觉状态：

HAND_APPROACH：手靠近

HAND_GRASP：手抓取

OBJECT_MOVE：物体移动

OBJECT_LEAVE：物体离开

再由业务逻辑组合成：

TAKE_OUT：取出

TAKE_IN：放入

NO_ACTION：没有发生操作

Gesture/Action输出：

deviceId

streamId

trackId

action

confidence

startTime

endTime

## 十一、业务事件

最终由Business Event Service将稳定的饮品身份和动作进行关联。

例如：

deviceId = device_001

trackId = track_023

productId = product_10001

action = OUT

confidence = 0.94

startTime = xxx

endTime = xxx

最终形成：

“设备001在xxx时间取出了product_10001饮品。”

业务事件通过RocketMQ发送给业务系统，业务系统负责后续库存、订单、记录等业务处理。

## 十二、模型解耦原则

各模型之间通过标准事件协议连接，而不是直接调用彼此内部代码。

Detection → 标准Detection Event → Tracking

Tracking → 标准Track Event → Recognition

Recognition → 标准Recognition Event → Temporal Aggregation

Temporal Aggregation → 标准Identity Event → Gesture

Gesture → 标准Action Event → Business

因此Detection模型、Recognition模型、Gesture模型都可以独立升级，只要输入输出协议保持兼容，下游服务无需修改。

## 十三、最终核心链路

实时链路：

Camera → Stream Ingest → Redis Stream/实时内存队列 → Detection → Tracking → Recognition → Temporal Aggregation → Gesture/Action → Business Event

可靠业务事件链路：

AI Pipeline → Business Event → RocketMQ → Business System → Database

视频存储链路：

Camera → Stream Ingest → 原始视频/关键帧 → Object Storage

三条链路分别承担实时计算、可靠业务事件传递和历史视频保存，不应该把所有职责混在Redis或RocketMQ中。
